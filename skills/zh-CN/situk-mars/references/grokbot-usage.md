# 在 GrokBot 中使用

本 Skill 是机器人军衔制奖赏制度，主体是报功、核功、人类批准、记功、授衔、周报。读取一套文档就能开展草案工作，不以机器人管理API齐全为前提。当前分发候选只在本地虚构环境演练，没有创建、修改或改名真实机器人，也没有操作routine。

## 客户首次接入

1. 客户指定组织、负责人稳定标识、运行目录、可读材料边界、业务目标、首次新功起算、现役名单、规则版本。未知目标保留未知，先不评三等目标路线。
2. 优先把客户已有的统筹机器人绑定commander，把无关联核验者绑定military_officer。绑定是名册登记，不自动改变平台职责或权限。岗位缺位时可由客户本人承接；生成[岗位说明](../templates/role-charters.md)及待创建建议，不自行创建。
3. 人类采纳rule_version，并分别批准运行目录、已有基线和具体操作范围。历史名单/分数/军衔缺批准凭证时待对账，不清零、不自动追授。
4. 先手动跑一个闭合周期。验证事件去重、回避、周帽、批准原记录、正式账与周报能对上，再讨论自动化。

客户业务梳理用于理解目标链和现有岗位：先复用人类、机器人或确定性工具，再提出确有独立交付缺口的岗位建议。补岗清单属于后续单独批准事项，不是本制度每次评奖都扩编的理由。

## 工具可用时怎样执行

在已有元帅或用户会话中，只用当前真实可见、参数已核实且获得授权的原生工具。不得假设工具一定叫CreateAgent，不能编造API地址、请求结构或默认行为。记录工具定义来源、观察时间、稳定对象ID和原始回执指针；没有回读就不能写“平台已生效”。

能力按动作分别标记：DOCS_ONLY（仅草案/人工作业）、OBSERVED_TOOL（定义可见）、EXECUTED（有实际回执）、READBACK_VERIFIED（有独立回读）。工具不存在只阻塞对应平台动作，不阻塞证据草案或纸面制度。

文字职责、共享账号中的文件目录约定不构成平台ACL。若不能强制限制军务官写正式账，标POLICY_ONLY并由人类监督，不声称权限隔离已验证。不能借元帅职位扩大工具权限。

创建机器人不是安装Skill，也不证明机器人能读到运行资料。将来客户明确授权创建时才考虑空白岗位，分别验证职责、资料可见性、是否附带routine/初始消息以及独立回读；调用结果未知先对账，不盲目再次创建。此候选版不提供该执行器。

## 本地核算与模拟

`scripts/merit_engine.py`是无网络的确定性核算模块；`scripts/simulate.py`使用虚构客户和证据标记演练。输出目录由调用者明确给出，位于已授权运行目录，不能写回Skill源码。

本地actor_id只是操作者声明，不验证真人身份；qualified、adopted、证据引用等输入也不证明事实为真。真实使用要由人类/军务官打开证据并确认来源，再把核实结果交给核算器。模拟器里的人类批准是合成演练，不能拿去批准真实奖赏。

从Skill根目录运行`python -B scripts/simulate.py --output ../.local/merit-demo-new`。目标必须是源码外的新目录；已有目录拒绝重置。产物包含simulation.json、六阶段文档、名册与正式账、周报和验收结果，不包含任何真实宿主执行回执。

能力边界：脚本可核算通常奖项、按批准记分、普通逐阶候选与批准登记、特授元帅单席及周报；复杂更正、撤奖、处分、破格、任命撤换走人工模板。没有任何平台改名、发消息、建岗、routine或外部发送调用。

## 每周军务文档

军务官手动形成军功周报、待复核清单和岗位观察。周报分别列已批准且已记分、已批准未登记、待核/待批、晋衔变更、特授与名号待同步、覆盖和缺口。汇报收件人、时间和调度方式由客户另行决定；“每周出报”职责不等于授权新建或启动routine。

首期先手动给人类验收。此后若另获授权采用现有调度，也要保持一个执行端，避免重复记账或重复通知；本 Skill 不为周报主动读取、修改、启停或触发任何routine。
