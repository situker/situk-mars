# 在 GrokBot 中使用

本 Skill 为 GrokBot 团队提供报功、核功、人类批准、记功、授衔和周报的文档工作流。先按规则和模板整理草案，不要求先接通机器人管理 API。随包演练只使用虚构材料，不创建、修改或改名真实机器人，也不操作 routine。

## 客户首次接入

1. 客户指定组织、负责人稳定标识、运行目录、可读材料边界、业务目标、新功起算时间、现役名单和规则版本。未知目标保持未知，三等功的目标路线先待补。
2. 优先把已有统筹机器人绑定为 commander，把无关联核验者绑定为 military_officer。绑定只做名册登记，不自动改变平台职责或权限。岗位缺位时，由客户本人承接；另可生成 [岗位说明](../templates/role-charters.md) 和待创建建议，本包不自行创建机器人。
3. 由人类采纳 rule_version，并分别批准运行目录、既有基线和具体操作范围。历史名单、分数或军衔缺少批准凭证时先待对账，不清零，不自动追授。
4. 先手动完成一个闭合周期，核对事件去重、回避、每周上限（周帽）、批准原记录、正式账与周报。它们一致后，再讨论是否另行授权自动化。

业务梳理用于说明成果与目标的关系、了解现有岗位。先复用已有的人类、机器人或确定性工具；确有独立交付缺口时，再提出岗位建议。补岗须单独批准，不能因每次评奖自动扩编。

## 工具可用时怎样执行

在已有统筹者或用户会话中，只用当前真实可见、参数已核实且获得授权的原生工具。不得假设工具一定叫 CreateAgent，也不能编造 API 地址、请求结构或默认行为。记录工具定义来源、观察时间、稳定对象 ID 和原始回执指针；没有回读就不能写“平台已生效”。

每项动作分别标记能力状态：DOCS_ONLY（仅草案或人工作业）、OBSERVED_TOOL（定义可见）、EXECUTED（有实际回执）、READBACK_VERIFIED（有独立回读）。缺少工具时，只阻塞对应平台动作，仍可整理证据和文档草案。

岗位文字和共享账号下的文件目录约定，不构成平台 ACL（访问控制）。若无法强制阻止军务官写正式账，标记 POLICY_ONLY 并由人类监督，不能声称已验证权限隔离。统筹岗位或元帅特授头衔都不能扩大工具权限。

创建机器人不等于安装 Skill，也不证明它能读取运行资料。今后只有客户明确授权创建时，才考虑缺位岗位，并分别验证职责、资料可见性、是否附带 routine 或初始消息，以及独立回读。调用结果未知时先对账，不盲目再次创建。本版不提供机器人创建执行器。

## 本地核算与模拟

`scripts/merit_engine.py` 是无网络的确定性核算模块，按相同输入和规则计算结果；`scripts/simulate.py` 使用虚构客户和证据标记演练。调用者须明确指定已授权的输出目录，不能写回 Skill 源码。

本地 actor_id 只是操作者声明，不能验证真人身份；qualified、adopted 和证据引用等输入，也不能证明事实为真。真实使用须由人类或军务官打开证据、确认来源，再将核实结果交给核算器。模拟器中的人类批准是合成演练记录，不能用于批准真实奖赏。

从 Skill 根目录运行 `python -B scripts/simulate.py --output ../.local/merit-demo-new`。系统命令为 python3 时，用 python3 替代 python。目标必须是源码外的新目录；不要预先创建最终目录，空目录也会被拒绝。产物包含 simulation.json、六阶段文档、演练名册与账本、周报和验收结果，不包含真实宿主执行回执。

脚本可核算常规奖项、按批准记分，检查普通逐阶晋衔候选并登记已批准晋衔，检查元帅单席特授并生成周报。复杂更正、撤奖、处分、破格和任命撤换使用人工模板。脚本不调用平台改名、发消息、建岗、routine 或外部发送工具。

## 每周军务文档

军务官手动形成《军功周报》《待复核清单》和《团队岗位观察》。分别列明已批已登记、已批未登记、待核或待批、晋衔变更、特授与名称待同步事项，以及已读范围和缺口。汇报收件人、时间和调度方式由客户另行决定；“每周出报”职责不等于授权新建或启动 routine。

首期先手动出稿，交人类验收。此后若另获授权采用现有调度，也须保持一个执行端，避免重复记账或通知。本 Skill 不为周报主动读取、修改、启停或触发任何 routine。
